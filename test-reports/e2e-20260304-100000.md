## Comparison: ERC-4337 vs Direct

| | ERC-4337 | Direct |
|-|----------|--------|
| **Actors** | 4 (Deployer, Sponsor, Bundler, Alice) | 2 (Deployer, Alice) |
| **On-chain txs** | 4 | 3 |
| **Alice pays gas** | ❌ (Sponsor/Bundler pays) | ✅ (pays own gas) |
| **Alice signs** | UserOp + delegation (both off-chain) | Delegation (off-chain) + sends tx |
| **Delegation carrier** | Bundler's type 4 tx | Alice's own type 4 tx |
| **Delegation persistent** | ✅ (set by third party) | ❌ (cleared after Alice's nonce increments) |
| **Requires EntryPoint** | ✅ | ❌ |
| **forge prompt workaround** | Not needed | `run-e2e.exp` (expect wrapper) |

## Key Insights

1. **EIP-7702 delegation signing**: Alice signs `(chainId, implementationAddress, nonce)` off-chain via `vm.signDelegation()`. The resulting `(v, r, s)` signature is embedded in a type 4 tx's authorization list. The EVM processes authorizations before execution, so delegation is active when contract calls run.

2. **Who carries the delegation matters**: When a third party (Bundler) carries Alice's delegation in their type 4 tx, the delegation persists on-chain. When Alice carries her own delegation, the nonce increment from the tx itself may clear it.

3. **forge + EIP-7702 quirks**:
   - `--gas-estimate-multiplier 500` needed (forge underestimates type 4 gas)
   - forge prompts "address contains no code" when calling Alice before delegation is set → use `expect` wrapper
   - Alice's nonce changes from authorization processing, causing nonce mismatch if Alice sends >1 tx → combine everything into one type 4 tx

4. **Deterministic Alice**: `keccak256("alice-...", block.number, block.timestamp)` ensures fresh keypair each run without env vars.
