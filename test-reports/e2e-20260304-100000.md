## Comparison: ERC-4337 vs Direct

| | ERC-4337 | Direct |
|-|----------|--------|
| **Actors** | 4 (Deployer, Sponsor, Bundler, Alice) | 2 (Deployer, Alice) |
| **On-chain txs** | 4 | 5 (3 setup + 2 Alice) |
| **Alice pays gas** | ❌ (Sponsor/Bundler) | ✅ (pays own gas) |
| **Alice signs** | UserOp (EIP-191) + delegation (off-chain) | Delegation (off-chain) + sends 2 txs |
| **Delegation carrier** | Bundler's type 4 tx | Deployer's type 4 tx |
| **Delegation persistent** | ✅ | ✅ |
| **Alice calls separately** | N/A (all via UserOp) | execute() + executeBatch() |
| **Requires EntryPoint** | ✅ | ❌ |

### Key: delegation must be carried by a third party

Both flows have a **third party** (Bundler or Deployer) carry Alice's delegation in their type 4 tx. This is required because:

1. EIP-7702 authorization **increments Alice's nonce** during processing
2. If Alice sends the type 4 tx herself, the auth nonce (0) and tx nonce (0) conflict
3. Etherscan shows `Validity: False` for self-carried delegations

## Key Insights

1. **EIP-191 signature**: UserOp hash is wrapped with `\x19Ethereum Signed Message:\n32` before ecrecover. Signing side must use `personal_sign`, not raw `eth_sign`. This prevents blind-signing attacks.

2. **Prefund gating**: Prefund is only paid when signature is valid (`validationData == 0`). Invalid signatures return `SIG_VALIDATION_FAILED` (1) without reverting.

3. **Delegation must be carried by third party**: Auth nonce and tx nonce conflict when Alice sends her own type 4 tx.

4. **forge + EIP-7702 nonce issue**: Forge doesn't account for auth nonce increments → split E2EDirect into two phases.

5. **Gas estimation**: `--gas-estimate-multiplier 500` needed for type 4 txs.

6. **Deterministic Alice**: `keccak256("alice-...", block.number, block.timestamp)` per run.
