### Key Difference: No UserOp Signature Needed

Direct execution path does not go through EntryPoint:
- No `userOp.signature` needed (no UserOp)
- No Paymaster
- Alice's EVM transaction signature is the authorization itself
- ERC-7821 `_erc7821AuthorizedExecutor` checks `msg.sender == address(this)` (Alice calls herself)

## Key Technical Notes

1. **Native EIP-7702 support via `initCode` marker** — UserOp `initCode` is set to `0x7702000000000000000000000000000000000000` (20-byte marker with `0x7702` prefix). This tells EP v0.8 to include the delegation address in the `userOpHash` (EIP-712), binding Alice's signature to a specific delegate implementation. Without this marker, `initCode` would be empty and the userOpHash would not commit to the delegation target.
2. **ERC-4337 v0.8 userOpHash is EIP-712** — Unlike v0.7 where `userOpHash = keccak256(packUserOp || EP || chainId)`, v0.8 uses EIP-712 typed data with the EntryPoint's domain separator (`name="ERC4337"`, `version="1"`). The hash can be computed locally since all domain parameters are public constants. For EIP-7702 accounts, `hashInitCode = keccak256(delegateAddress)` replaces the raw `keccak256(initCode)`, binding the signature to a specific delegate. Local computation has been cross-verified against `EP.getUserOpHash()` on Sepolia.
3. **OZ SignerEIP7702** uses raw ECDSA: `ecrecover(hash, sig) == address(this)`. UserOp signatures have no EIP-191 prefix.
4. **VerifyingPaymaster** uses **EIP-712 typed data** with domain separator (binds to chainId + paymaster address) for replay-proof authorization. Includes Ownable2Step, Pausable, ReentrancyGuard, and signer/owner separation.
5. **ERC-7821 mode** `0x01000000...` = batch call type, using ERC-7579 execution encoding.
6. **Execution encoding**: `abi.encode(Execution[])` where `Execution = (address target, uint256 value, bytes callData)`.
7. **vm.setNonce workaround** still needed — forge simulation does not model EIP-7702 auth nonce increment.
8. **`--gas-estimate-multiplier 500`** required for type 4 transactions but causes over-estimation for type 2 txs from delegated accounts.
9. **Paymaster cleanup is two-phase**: Step 7 in E2EPaymaster calls `unlockStake()` + `withdrawTo()`. A separate `PaymasterCleanup.s.sol` script handles `withdrawStake()` after `unstakeDelay` has elapsed. This is due to a forge limitation: simulation runs all txs in a single EVM pass, so `unlockStake()` + `withdrawStake()` in the same script fails with "Stake withdrawal is not due".
